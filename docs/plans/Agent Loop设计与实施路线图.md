# 库解 Agent Loop 设计与实施路线图

日期：2026-11-21（Asia/Shanghai）  
状态：设计稿；本文件不代表循环、工具或配置已经实现。  
基线：`c049f3f`，沿用现有工作区权限规则和知识库检索链路。

## 1. 目标与首版范围

让系统在证据不足时，有依据地改变检索方法、补读正文，再决定回答、澄清或说明资料缺失。简单问题首轮完成；复杂问题才继续循环。

首版处理当前用户有权使用的知识库，支持改写检索、少量问题拆分、读取已命中资料的相邻页或父块。沿用 BM25、向量召回、融合、重排、来源引用和服务端会话。账号、资料上传与删除仍走现有接口。

当前已有多查询扩展、充足度判断和一次答案修正，但尚未形成“根据本轮结果决定下一次检索”的循环。现有 `AdaptiveQueryOptimizer` 负责查询准备，不能在循环内部再启动一个没有预算约束的独立 Agent。

首版采用 Python 显式状态机，接入现有 `pipeline`，不新增框架迁移任务。LangGraph 官方的[检索、评估与改写示例](https://docs.langchain.com/oss/python/langgraph/agentic-rag)可作为流程参考；其[状态、节点和条件边模型](https://docs.langchain.com/oss/python/langgraph/graph-api)适合后续需要检查点、暂停恢复时再评估。本文的预算、权限和验收要求是本项目的设计选择。

## 2. 用户实际会得到什么

| 场景 | 循环的处理 | 终点 |
| --- | --- | --- |
| “5A是什么” | 首先查知识库，读取术语定义；证据足够即退出 | 简短解释五项内涵并引用来源 |
| “奖学金的奖金”→补充奖项名称 | 保留奖金目标；只找到条件时，围绕奖励标准继续查 | 回答已证实的金额，或说明未列金额 |
| 命中目录、章节名 | 按同一文档的来源标识补读父块或相邻页 | 使用正文作答，目录不能独立支撑结论 |
| “这两类奖学金有什么区别” | 按缺少的比较项分别查证，合并去重 | 每个比较项有对应证据 |
| 多个年份标准不同 | 能按适用年份分别说明就直接列出；需要判断个人适用标准时才问年份 | 有范围说明的答案或一个必要问题 |
| 索引内没有所问事实 | 尝试有区别的补检，识别无新增证据 | 明确缺少什么，不不断追加学院、学年等条件 |
| 服务超时或调用失败 | 有界重试并记录故障 | 说明暂时无法完成检索，不冒充资料不存在 |

## 3. 主流程和状态转换

```text
身份与检索范围校验 → 意图路由 → 还原完整问题 → 首轮检索 → 证据评估
                                                             │
    ┌────────────────────────────────────────────────────────┤
    │ 足够                                                   │ 不足
    ▼                                                        ▼
生成受来源约束的草稿 ← 再评估 ← 执行补检/补读 ← 校验动作与预算 ← 选择下一步
    │                                                        │
    ▼                                                        ├─ 必须由用户选择的歧义 → 澄清并结束
来源、数值和安全核验                                         ├─ 无进展/预算耗尽 → 已证实部分或缺失说明
    ├─ 通过 → 发布最终答案并结束                              └─ 权限变更/取消/故障 → 对应终止状态
    └─ 失败 → 在剩余预算内修正一次并重新核验
                    └─ 仍失败 → 不发布未核验结论
```

程序强制执行状态转换。模型的“可以回答”只是一个动作建议，不能跳过最终核验。知识型问题必须先检索；明确问候、感谢和助手能力咨询保留闲聊入口。

证据评估不再只返回一个布尔值，而返回结构化结果：

- `sufficient`：是否足以支撑当前问题。
- `missing_facts`：缺少的具体事实，例如奖金金额，而不是泛泛的“信息不足”。
- `supported_fact_ids`：能够支持当前答案的证据编号。
- `ambiguity`：存在什么互斥口径、对应哪些来源，是否确实需要用户选择。
- `next_action`：建议补检、补读、回答、澄清或停止。

无证据的“学校可能不同”“年份可能不同”不能独立构成追问依据。

## 4. 可调用动作及权限边界

动作采用枚举和结构化参数。首版可通过模型 JSON 决策驱动，不依赖模型厂商必须支持某种工具调用协议。

| 动作 | 输入 | 返回 | 程序限制 |
| --- | --- | --- | --- |
| `search_knowledge` | 查询词、需要补齐的事实 | 带稳定来源 ID、页码、版本和分数的证据 | 复用现有召回与重排；范围由服务端注入 |
| `read_source` | 已命中的证据 ID、父块或前后页偏移 | 对应正文及定位信息 | 仅限已命中文档；每次最多两页；缺少页码时读取父块或元素邻接 |
| `answer` | 拟使用的证据 ID | 进入程序控制的生成与核验阶段 | 不能直接把动作文本当最终答案 |
| `clarify` | 有来源依据的歧义及最小问题 | 一个澄清问题并结束本轮 | 不重复已明确的信息；不询问资料本身缺失的答案 |
| `stop` | 结构化原因 | 缺失说明、部分答案或故障提示 | 原因由程序映射为对应终止状态 |

查询改写或拆分由证据评估给出，首版每次只执行一个补检目标，再根据结果决定是否继续。

模型不能传入用户身份、任意工作区、文件路径或数据库过滤表达式；工具层从请求上下文取得这些信息。每次工具调用及最终发布前重新检查权限版本，撤权后停止，不再返回已失去权限的正文和引用。

本设计不授予网页搜索、任意 SQL、Shell、文件写入、资料删除或索引修改能力。检索范围不能因为当前没有结果而扩大。

## 5. 每次请求保存的状态

首版状态只在本次请求中存在；完整规划过程不写进用户聊天历史。会话中保存原始用户消息和最终公开回复，后续澄清轮次再从服务端历史恢复目标。

| 状态组 | 主要字段 |
| --- | --- |
| 问题 | `original_question`、`effective_question`、最新用户约束、待补事实 |
| 请求身份 | 服务端用户 ID、可用工作区、权限版本、知识库版本 |
| 执行 | 当前阶段、检索轮次、已执行查询和补读动作、截止时间、取消信号 |
| 证据 | 来源 ID、工作区、文档版本、块/页、文本、相关性及支持的事实 |
| 预算 | 剩余查询数、补读数、模型调用数、上下文容量、已用 token |
| 结果 | 最终状态、终止原因、核验结果、最终引用 |

证据按“工作区＋文档版本＋块/页”去重。补检结果加入同一个证据池，不能用新一轮结果整体覆盖前一轮有用证据。生成前按问题相关性和事实覆盖压缩证据，避免拼入整份文档。

## 6. 循环预算和退出规则

以下为拟议初始值，P0 测得现有耗时与模型调用量后再定稿，不是已经存在的配置。

| 预算 | 初始建议 | 计数口径 |
| --- | --- | --- |
| 检索轮数 | 最多 3 轮 | 首轮 1 次，最多补检 2 次 |
| 查询变体 | 全请求最多 5 条 | 首轮沿用最多 3 条；后两轮各留 1 条；拆分也计数 |
| 正文补读 | 最多 2 次 | 每次最多两页或等量父块文本；同一位置不重复读 |
| LLM 调用 | 最多 12 次尝试 | 分类、还原、规划、生成、核验和重试都计入；优先预留 4 次给生成及核验修正 |
| 单次网络重试 | 最多 1 次 | 仅针对可重试故障，仍消耗调用数与时间预算 |
| 总时限 | 建议 120 秒 | 每次调用超时取服务配置与剩余预算较小值；不能在外层超时后仍后台重试 |
| 生成上下文 | 最多约 14,000 字符 | 同时设置模型 token 上限；来源文本和模型输出都受限 |

实际流量的预算应依据 P0 的 P50/P95 调整。超过成本预算时，不能通过放宽来源核验或让通用常识兜底作答来“完成任务”。

Embedding 和 Rerank 的请求另按服务类型计量，受查询、工具预算与总时限共同约束；成本报告不能只统计 LLM 而忽略这两类调用。

遇到以下任一条件必须退出：

1. 所问事实已覆盖，进入生成核验。
2. 待执行查询与已有查询等价，且没有新的缺失事实或阅读位置。
3. 一次补检没有新增有效证据，且没有尚未执行的明确正文位置可读。
4. 达到检索、工具、模型、token 或时间上限。
5. 需要用户选择的真实歧义无法从资料消除。
6. 用户取消、登录失效、权限变更或不可恢复的服务故障。

无新增证据必须按稳定 ID 和事实覆盖计算，不能由模型一句“还需要继续查”覆盖。多次重复的错误动作最多进行一次结构化纠正，然后结束。

## 7. 答案发布、核验与前端状态

### 7.1 先核验再公开事实

当前流式链路会在最终核验前发送草稿 token。首版循环接入时，应先发送状态事件，暂存草稿；核验通过后再分块发送最终内容。界面不能把这段分块展示描述为未经缓冲的模型实时生成。

后续确需更低首字延迟时，可单独评估逐段核验后发布；它不属于首版交付范围。

### 7.2 核验不能由 Agent 绕过

- 明确的无来源金额、分数、时间或结论必须拒绝发布；模型不能降低阈值。
- 现有 `apply_hallucination_threshold` 存在按置信度将失败检查放行的路径。P1 必须把确定的来源矛盾/无依据数值与可校准的软评分区分开，确保前者不因用户调低阈值而通过。
- 最多允许一次答案修正；若需要新证据，只有仍有补检预算才允许返回检索阶段，不能重置计数。
- 最终引用只包含实际支持答案的证据，不把所有候选片段都展示为依据。
- 部分答案也必须核验；缺失部分明确标注，不能用“部分回答”绕过核验。

### 7.3 用户看到的状态

沿用 `status` 事件，增加可选的阶段、轮次与状态 ID：正在查找资料 → 正在补查奖励标准 → 正在读取相关正文 → 正在核对答案。只公开动作摘要，不公开模型内部推理。

终止状态明确区分 `answered`、`partial`、`needs_clarification`、`insufficient_evidence`、`budget_exhausted`、`timeout`、`cancelled`、`permission_changed` 和 `failed`。先交付预算与停止能力，再考虑更复杂的过程面板。删除、上传等操作继续使用各自进度，不能触发问答思考动画。

取消需要传播到工具和模型连接。若底层调用无法及时取消，该请求应停止发布并禁止启动后续动作，同时在日志中记录尚未结束的调用。

## 8. 缓存和可观测性

仅缓存已核验的最终知识答案；不缓存规划中间结果、失败草稿、故障提示或首版的资料不足结论。缓存键保留当前用户、授权范围及版本、知识库版本、完整问题与用户约束，并加入循环策略版本。使用缓存前仍复核当前权限。

记录请求 ID、策略版本、各动作类型、耗时、轮次、证据数量变化、终止原因、模型调用和 token 消耗。查询及异常摘要脱敏；日志不保存密钥、私聊原文或完整模型推理。模型未返回用量时标为未知，不能伪造零消耗。

## 9. 分阶段路线图

| 阶段 | 工作内容 | 可评审交付物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| P0：建立基线 | 整理真实问题，记录当前路由、召回、答案和耗时；确认每个新工具的数据来源 | 至少 50 个去标识化用例、标注来源、现状报告、预算草案 | 用例包含有答案、真缺失、冲突、跨页及多轮；失败可定位到具体环节 |
| P1：最小闭环 | 结构化证据评估、关键词补检、统一状态与预算；接入知识优先路由及不可绕过的核验 | 能运行的三轮内循环、停止原因、功能开关、确定性工具测试 | 首轮命中直接结束；一次补检可补齐金额；重复查询及上限一定终止；未核验草稿不公开 |
| P2：补读正文 | 按来源 ID 读取父块/邻页；证据池去重与事实覆盖；精简最终引用 | 正文读取工具、来源定位、多事实比较用例 | 目录命中可找到正文；不能读入无权工作区；缺页明确反馈；旧有效证据不丢失 |
| P3：交互和中断 | SSE 阶段进度、停止生成、超时/撤权处理；统一会话和缓存策略 | 同步/流式一致的接口、可取消前端、脱敏追踪 | 每个终止状态都有正确 UI；取消后无后续工具调用；删除不显示 AI 思考 |
| P4：对照验收与逐步开放 | 用同一资料快照对比原链路和循环；测真实模型及服务故障；配置小范围开启和回退 | 质量/延迟/调用量对照报告、上线检查和回退步骤 | 满足下表门槛，才扩大到默认开启 |

首个可用版本以 P1 为节点；P2 和 P3 完成后才具备本文定义的首版试运行条件。P4 决定是否默认开启。阶段工期在 P0 明确现状和验收数据后估算，不预先承诺上线日期。

### 首版验收门槛（建议）

| 项目 | 通过条件 |
| --- | --- |
| 知识路由 | 标注为知识问题的测试集全部进入检索；问候与能力咨询的固定回归不退化 |
| 简单问题 | 本来首轮有答案的用例不因开启循环而增加补检轮次 |
| 关键缺证场景 | 5A、奖学金奖金、多轮补类别、目录转正文、跨页条件等固定用例全部通过 |
| 安全及退出 | 越权、撤权、提示注入、数值无依据、死循环、取消和超时用例全部通过 |
| 答案质量 | 50 题集的人工证据支撑通过率目标不低于 90%，且不低于原链路；分类报告不能用平均分掩盖安全失败 |
| 补检收益 | 在标注“首轮不足、补检可得”的子集中，已证实答案率高于原链路；若无收益，先修策略再上线 |
| 性能及成本 | 简单问题 P95 耗时建议不超过同快照基线的 1.2 倍；复杂问题遵守硬预算；报告每题调用量及可获得的 token 用量 |
| 部署回退 | 关闭开关即可恢复原问答路径，不删除资料、不重建向量库、不更改账号数据 |

90% 与 1.2 倍是拟议验收目标，不是当前测得结果。测试集要保留独立验收部分，不能全部作为提示词调试样本。

## 10. 代码落点和最小改造顺序

| 文件/模块 | 计划修改 |
| --- | --- |
| `manufacturing_rag/agent_loop.py`（新增） | 请求状态、动作与预算执行器、证据池、退出控制；函数式节点便于单测 |
| `manufacturing_rag/pipeline.py` | 提取可复用的检索和核验步骤，接入循环开关；保留原路径；统一生成发布入口 |
| `manufacturing_rag/adapters/llm.py` | 结构化证据评估与动作建议；生成只使用选中的证据；规划不直接输出最终事实 |
| `manufacturing_rag/adapters/query_optimizer.py` | 复用问题还原与改写；所有内部模型调用受同一预算约束 |
| 检索器/原文存储适配层 | 实现只读 `read_source`；来源 ID 到页/父块的映射必须稳定并受权限控制 |
| `manufacturing_rag/api.py`、`schemas.py`、`config.py` | 注入身份与取消上下文；增加可选终止信息和拟议 `RAG_AGENT_LOOP_*` 配置；保留兼容字段 |
| `frontend/src/App.jsx` | 显示动作进度、停止操作、处理最终状态；继续将问答状态与其他操作分开 |
| 测试与评测脚本 | 工具序列、预算、权限、事件顺序的确定性测试，以及真实模型对照报告 |

建议实施顺序：先抽出单次检索步骤并保持现有用例通过，再加结构化评估和一次补检，最后扩展至预算内的三轮和补读正文。无需先重写整个前端、数据库或向量索引。

## 11. 发布与回退

开关默认关闭；先在固定资料快照验收，再按服务器控制的测试账号或工作区小范围开启。客户端不能自行指定任意策略或提升预算。初期不做全量影子调用，避免未经测量的双倍模型成本。

每阶段只提交与该阶段相关的代码和文档。推送成功后按既有生产流程发布所涉及服务。若出现答案质量、权限、成本或延迟退化，关闭循环开关恢复原路径；保留脱敏追踪以定位原因。

本次交付为路线图设计文档，尚未启用 Agent Loop，也未改变线上服务行为。
