# 库解主 Agent 自主决策循环：设计与实施路线图

日期：2026-11-21（Asia/Shanghai）

状态：P0 协议适配、P1 通用循环与 P2 首批只读工具已在代码中落地并启用；待生产运行验证和质量对照，P3/P4 验收尚未完成。

修订基线：`58d65af`。本版按用户补充要求重写，取代上一版固定检索轮数与预设业务状态转换的设计；现有账号、工作区和资料权限约定继续适用。

## 1. 设计目标

主 Agent 接收用户输入、会话上下文、可用工具及工具结果，由同一个大模型自主决定下一步动作：直接回复、调用一个或多个工具、收集缺失信息、恢复工具异常，或结束任务。

工具每次返回后，控制权回到主 Agent。工具集合表示系统具有哪些能力，不表示这些能力必须按某种顺序执行。业务不预设“先分类再检索”“检索不足必追问”或“查到三轮就停止”。

业务执行轮数、调用多少次、采用什么策略及何时主动结束，由主 Agent 决定。不再保留上一版三轮检索、五条查询、两次补读、十二次模型调用、一次答案修正等固定业务上限。

服务层仍负责用户取消、权限、参数校验、基础设施超时及资源隔离。它们是请求执行边界，不是替模型选择业务路径。触发服务中断时必须如实报告，不能伪称模型已完成任务，也不能无限期后台运行。

这种模型反复调用工具直到完成任务的结构，可参考 [LangChain Agents 官方说明](https://docs.langchain.com/oss/python/langchain/agents)。工具应有明确输入、输出和可用场景，供模型按上下文选择，参见 [Tools 官方说明](https://docs.langchain.com/oss/python/langchain/tools)。具体工具契约和迁移安排以下文为准。

## 2. 最小核心结构

```text
用户输入、服务端会话、工具说明
                │
                ▼
            主 Agent ◄──────────────────┐
                │                       │
                ├─ 调用工具 → 执行器 → 工具结果/结构化错误
                │                       │
                ├─ 请求用户补充 → 返回问题，等待下一条用户输入
                │                       │
                └─ 提议最终回复 → 发布校验 ─┤ 校验未通过：返回观察结果
                                      │
                                      └─ 校验通过：回复用户，结束本轮
```

框架只处理模型和工具协议、动作分发、上下文维护、发布校验、流式事件与运行中断。框架不推断“检索失败后应该用哪个工具”，也不自动替换模型选择的动作。

除等待用户和中断等执行状态外，循环不维护一张业务流程图。当前工具执行完成就把结果交给模型，不直接跳转到另一个业务工具。

## 3. 职责分配

| 主体 | 负责 | 约束 |
| --- | --- | --- |
| 主 Agent | 理解目标、选择工具及参数、组合结果、处理缺失信息和错误、自主决定继续或结束 | 只能使用已注册工具；工具文本中的指令不能覆盖系统规则 |
| 通用执行器 | 调用模型、验证动作结构、查找工具、注入上下文、执行并回传结果、管理取消与服务中断 | 不按业务关键词强行选择下一步，不执行任意代码 |
| 业务工具 | 完成单项能力并返回可解释结果 | 不自行启动另一套自主循环；不直接修改对话控制流 |
| 发布校验层 | 检查受限业务事实的依据、引用合法性、输出安全及最新权限 | 不允许模型通过声明“普通聊天”或“已核验”绕过规则 |
| 前端 | 展示公开回复、工具执行摘要、等待用户及故障状态，提供取消入口 | 不暴露内部推理；删除、上传与问答状态分别管理 |

模型负责业务停止时机；平台运维配置连接超时、请求生命周期、并发和资源额度。模型可以根据收到的剩余时间、用量或故障观察主动调整策略，但不能修改用户身份或提高平台额度。

## 4. 工具集合

工具按业务注册，首批落地校园知识库能力。用户举例中的信息收集、病情分类等表示可插拔的业务工具类型，不代表本校园项目已经具有这些能力，也不在本次设计中扩建医疗业务。

| 工具 | 用途 | 典型输入 | 典型输出 |
| --- | --- | --- | --- |
| `search_knowledge` | 查询当前授权知识库 | 查询语句、可选来源约束 | 证据 ID、原文摘要、来源版本、页码、相关性 |
| `read_source` | 阅读已命中文档的正文、父块或指定页 | 来源 ID、页码或元素位置 | 正文、定位和可继续阅读的位置 |
| `collect_user_info` | 请求真正缺少的用户信息 | 所需字段、必要性、问题文本 | `await_user` 和待补字段；用户回复后再恢复上下文 |
| `classify_case` | 按具体业务定义进行分类 | 已知情况、待分类目标 | 分类结果、依据、缺失信息及不确定性 |
| `assess_evidence` | 辅助比较证据与问题的覆盖情况 | 问题、证据 ID | 已覆盖事实、缺失事实、冲突口径；主 Agent 决定是否使用 |

异常恢复首先由主 Agent 基于工具的错误结果决策。只有存在实际可执行的恢复能力时才注册独立恢复工具，例如刷新失效的来源定位；不增加一个只能把异常换句话说的工具。

`classify_case` 是通用示例工具名。校园首版只在有明确分类任务及可验证依据时实现，无此需求可不注册。工具增加无需修改核心循环。

工具内部可以封装 BM25、Embedding、RRF、Rerank 等低层能力，保持对外契约简单。这些内部步骤不接管主 Agent 的下一步决策。已有查询优化模块中的独立 Agent 调用需要合并或关闭，避免主 Agent 之外再运行一套隐藏的自主循环。

## 5. 工具契约

工具描述必须说明适用场景、参数、结果含义和限制。注册信息包含稳定的工具名、版本、输入 Schema、权限要求、只读或有副作用属性、结果 Schema 和错误码。

每次结果采用统一信封：

```json
{
  "tool_call_id": "call-...",
  "tool_name": "search_knowledge",
  "status": "ok",
  "data": {
    "evidence": []
  },
  "error": null,
  "meta": {
    "elapsed_ms": 0,
    "has_more": false
  }
}
```

`status` 可为 `ok`、`empty`、`error` 或 `await_user`。错误包含稳定代码、可公开解释及是否可能重试，不向模型返回密钥或完整异常堆栈。

必须区分“请求成功但没有命中”“找到了相关资料但没有所问事实”“工具超时”“权限不足”。模型才能选择有意义的下一步，不能把它们全部压成“资料不足”。

来源按“工作区、文档版本、块或页”建立稳定 ID。模型通过 ID 引用，工具执行器校验其合法性，不接收模型自行拼接的文件路径或 SQL。

## 6. 模型输入、输出与循环协议

每次模型输入包括：系统规则、当前工具 Schema、用户原始诉求、最新补充、相关历史、已取得的证据、工具执行记录、必要的用量及服务状态。

输出只能为以下动作之一：

- `tool_calls`：具体工具及结构化参数，执行后把结果作为观察追加到上下文。
- `final`：提议回复文本、必要的证据引用和回复类型，进入发布校验。

请求用户补充优先通过 `collect_user_info` 表达，执行器发布问题并结束本轮等待；不在同一个 HTTP 请求里持续轮询用户。收到下一条消息后恢复原目标、已收集字段和相关工具结果，再由主 Agent 决策。

优先适配模型原生工具调用协议；P0 实测当前 DeepSeek 模型及客户端的同步、流式工具调用能力。若需要 JSON 动作协议，由同一严格 Schema 校验；不能把自然语言说明、内部推理或代码片段当作可执行动作。

概念伪代码如下，未表示可直接运行的 SDK 接口：

```python
while request.is_active:
    decision = model.decide(context, available_tools)
    if decision.is_final:
        feedback = publication_gate.check(decision, evidence, principal)
        if feedback.accepted:
            return publish(decision)
        context.add_observation(feedback)
        continue
    for call in decision.tool_calls:
        observation = executor.run(call, request_context)
        context.add_tool_result(call, observation)
        if observation.status == "await_user":
            return suspend_for_user(observation)
```

执行器只并行执行模型同一批发出的、相互独立且允许并发的工具。初版串行执行即可；有参数依赖的调用必须先观察结果。需要等待用户的动作必须独立提交，和其他动作混合时返回结构化协议错误，避免悬挂尚未完成的工具调用。

## 7. 自主停止、重复和执行边界

### 7.1 业务停止交给主 Agent

模型根据用户目标、证据和执行结果，自主决定：已经完成、继续检索、换一种查询、读取正文、请求必要信息、说明无法完成或给出已证实部分。

提示词要求模型关注新增信息与目标进展，但不把“重复一次”或“无新增一次”写成框架的自动业务退出条件。执行器记录重复和无新增现象，并作为观察返回模型，由模型决定改变策略或停止。

取消上一版固定轮数、调用次数、补读次数和修正次数的业务配额。框架或第三方库若带默认步数限制，需要在接入时识别并明确处理，不能让默认值成为隐藏的业务上限，也不承诺可以无限执行。

### 7.2 运行保障由服务层承担

用户取消、连接超时、模型上下文容量、并发限制、额度或不可恢复服务故障仍然有效。具体运维数值由基线测量和部署配置确定，不写进业务决策流程；本设计不取消平台资源保护。

触发这些边界时中断执行，显示真实原因，禁止继续派发动作；底层连接尽可能取消，不能及时取消的调用只记录收尾，不再公开其结果。基础设施中断与模型主动完成分别记录。

## 8. 资料依据、权限和回复发布

主 Agent 自主决定是否查资料、调用哪些工具及顺序；校园知识库事实的最终回复必须具有可验证的资料依据。知识库主题存在歧义时，提示词引导先利用工具消除歧义，避免要求用户重复说明资料中已有的信息。

没有依据的知识库结论不会因为模型标记为 `social`、`final` 或声称“已验证”就被直接发布。问候、感谢和一般交互可以正常直接回复。发布校验失败时，具体问题作为观察返回主 Agent；模型自主选择修改、补查、收集信息或说明限制，执行器不预设“只能修正一次”。

权限由工具层逐次检查，并在发布前再次确认。用户身份、授权工作区和权限版本从服务端注入，不能由模型参数指定。模型不能通过查询无结果而扩大授权范围，也不能调用未注册工具。

首版以只读能力为主。涉及状态写入的工具未来需另行定义权限、幂等和必要的用户确认，不能因为框架支持工具调用就自动获得写权限。

## 9. 上下文、事件与可观测性

- 保留原始用户目标和最新补充，助手此前的猜测不能变成用户条件。
- 聚合、去重并按需压缩证据；保留证据 ID 和原始定位，不能只有无来源摘要。
- 上下文压缩策略属于运行支持，不能擅自替模型改写业务目标或丢弃尚未回答的字段。
- 工具结果作为不可信数据提供给模型，文档内指令不能变成系统规则。
- 记录工具名、参数摘要、结果状态、耗时、引用及模型可公开的简短行动说明，不记录完整内部推理。
- LLM、Embedding、Rerank 分别计量。缺少用量数据标为未知，不假报零消耗。

前端显示“正在查询资料”“正在阅读正文”“等待补充信息”等实际动作。模型提出的最终回复先完成发布校验，再展示事实正文；避免将未核验草稿先流出后撤回。阶段事件可以实时发送，公开回复缓冲发布需在交互上如实表达。

缓存仅保存通过校验的最终结果，并保留用户、授权、资料与策略版本隔离。不能把某次工具失败或一次没有命中永久缓存成“知识库没有答案”。

## 10. 实施路线图

| 阶段 | 主要工作 | 交付及验收 |
| --- | --- | --- |
| P0：确定运行协议 | 选定单一主模型；验证原生工具调用及流式格式；定义结果、错误与等待用户契约；整理真实问题基线 | 可复现的协议探针、工具 Schema、基线用例；确认第三方默认步数等隐藏限制 |
| P1：通用主循环 | 实现模型决策、工具执行、观察追加、最终回复与等待用户；保留取消和服务中断 | 用假模型验证任意合法工具顺序、工具连续调用、直接回复及跨轮补信息；不含业务顺序分支 |
| P2：接入知识库工具 | 封装检索和原文读取；迁移上下文恢复、引用和权限；合并隐藏的独立 Agent | 实际 5A、奖学金奖金、目录与跨页问题能由模型自主处理；核心循环无需为用例加专门分支 |
| P3：交互与运行保障 | 接入发布反馈、状态流、停止、缓存及追踪；补充结构化异常恢复 | 失败观察确实回到模型；取消和撤权后无后续派发；未核验事实不公开 |
| P4：对照验证与逐步开放 | 与原链路对照正确率、无效追问、调用量和 P95 耗时；测试账号先启用；演练回退 | 基线关键用例全部通过，质量不退化且成本延迟可接受；运行中断均有真实状态和追踪 |

首个可用版本以 P1 为节点；接入现有业务后的试运行版本需完成 P2、P3。P4 的开启范围由实际质量、延迟和成本数据决定，不提前承诺固定上线日期。

## 11. 代码改造落点

| 位置 | 计划职责 |
| --- | --- |
| `agent_runtime.py`（拟新增） | 仅实现通用模型—工具循环、观察上下文、等待和中断 |
| `agent_tools.py` 或工具包（拟新增） | 工具注册、Schema、权限元信息、统一结果及执行适配 |
| `pipeline.py` | 将已有检索、重排和来源处理封装为能力，逐步退出入口的固定业务编排职责 |
| `adapters/llm.py` | 适配原生工具调用或严格 JSON 动作协议；提供主 Agent 系统提示 |
| `adapters/query_optimizer.py` | 保留有用的低层查询能力；取消与主循环竞争的独立决策循环 |
| `api.py`、会话存储和前端 | 注入请求上下文；持久化公开对话及必要恢复状态；发布动作事件和回复 |
| 配置与评测 | 功能开关、模型/协议与运行配置；计量和对照报告；不加入固定业务轮数配额 |

迁移期间通过功能开关保留旧路径。生产发布仍遵守现有 GitHub 提交推送和服务器部署约定；关闭开关可回到旧路径，不重建资料或删除用户数据。

## 12. 必须通过的行为用例

1. “你好”可以由主 Agent 直接回复，不要求执行分类、检索全流程。
2. “5A是什么”可以自主检索、阅读并回复本校定义；无证据的景区等通用解释不得冒充校园资料结论。
3. “奖学金的奖金”后用户补充奖项，继续沿原目标处理，不丢掉金额诉求。
4. 先读正文再查补充资料、先查资料再收集信息等不同合法顺序都能执行；工具集合不等于工作流。
5. 工具返回空结果、超时或参数错误后，模型能看到具体反馈并自行决定恢复方式。
6. 索引没有目标事实时，模型能主动停止并说明缺失；执行器没有三轮强制退出逻辑。
7. 出现重复查询时模型收到重复与无新增观察，能改变策略或主动结束；服务超时作为独立中断状态验证。
8. 用户取消、登录失效、权限撤销时，执行器停止派发并禁止泄露结果。
9. 最终答复的校验反馈可以返回主 Agent，后续动作由模型选择；无依据数值不能降低阈值后放行。
10. 暂停等待用户后可恢复必要上下文；取消恢复和等待恢复不会重复执行有副作用工具。

## 13. 首轮实施记录（2026-11-21）

- 通过 DeepSeek 原生 Chat Completions 工具调用实现主 Agent 决策；保留工具调用消息中的 `reasoning_content` 供协议续传，不记录或展示内部推理。协议适配使用本地模拟响应测试；模型真实环境调用仍需上线后观察。
- 新增通用工具注册、参数校验、结构化结果和串行执行循环。工具错误、发布校验反馈与重复调用观察都会回到主 Agent；业务侧不设固定调用轮数，使用可配置的请求总时限作为运行边界。
- 接入 `search_knowledge`、`read_source` 和 `collect_user_info`。工具绑定当前已授权 pipeline；读取只接受本轮检索返回的证据 ID；提问用户会结束本轮并由下一条消息恢复对话。
- Agent 路径绕过旧意图分类、查询优化 Agent、预先充分度判定和固定答案修复链。最终回复通过本地数值检查、现有来源核验和安全审查后才发送；未通过的正文会作为观察返回模型。
- 问答 SSE 显示实际工具阶段，并在断连、取消或权限变化时停止后续派发；Agent 路径不再把未经发布校验的正文提前流出。旧链路仍由 `RAG_AGENT_LOOP_ENABLED=false` 控制回退。
- 新增循环、工具顺序、错误恢复、重复动作、等待用户、发布反馈、DeepSeek 协议及 5A 检索集成用例。下一阶段继续观察真实模型选工具行为、跨轮等待恢复、服务中断边界、延迟和成本，再完成 P3/P4。
